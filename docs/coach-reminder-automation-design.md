# Shared Coach reminder options

Simon requested MATCH/TRAINING availability reminders, squad reminders and configurable deadline strictness in Slack C0C5N2XEQHM/1790926427.123419. Clarifications: 1790926851.154569, 1790927543.799169, shared team ownership 1790930398.560359 and stopping rules 1790931365.547819.

## Behaviour

One policy belongs to the team and is shared by its authorised Coaches. Every automation starts off and every timing starts blank. A Coach must configure hours/days and explicitly opt in. Save commands have durable identities, repeated clicks coalesce, retries reuse their identity, and conflicting edits require reload.

Only newly created, successfully delivered MATCH/TRAINING availability invitations after both the policy and release activation cutoffs are enrolled. Account-joining invitations, existing invitations and existing attendance are untouched. First confirmed delivery is immutable; resends never reset the elapsed clock. Changing a policy starts a new future-only cutoff and invalidates its previous jobs.

Individual reminders stop as soon as the shared status leaves awaiting, including Maybe. Deadline options are reminders only, exclusion of awaiting/Maybe from planning, or automatic Not attending for awaiting plus notification. Maybe remains an explicit answer and can be excluded under strict policy; it is never automatically replaced. Automatic status is a separate effect with coach_deadline_automation provenance, projected into reads rather than written into a parent's answer. Late Attending or Not attending supersedes the automatic effect. Late Attending restores eligibility without rewriting a saved squad. Existing response APIs remain open until their existing event-based closing rules.

A persisted selected squad decision stops the squad reminder. Current active authorised assigned team Coaches receive it through their existing Coach inbox/push invitation preference. Parent/player availability notifications reuse existing eligible contacts, app/email/both preferences, active links, installation opt-outs and the existing plan gate. No new Coach email fallback is invented.

Simon approved protecting players whose last linked Parent is removed or revoked (1790962092.518319, following the explanation at 1790961988.074769). Parent-dependent automatic deadlines require current eligible linked Parent authority independently of app/email preferences. Discovery/worker evaluation skips a deadline without an eligible responder; the raw commit snapshot detects authority loss before commit, and SQL rejects an automatic Not attending effect without an eligible Parent or existing verified adult self-responder. Recorded effects remain audit records, but current projections and automatic-mode planning guards stop applying them while no eligible responder remains. Explicit Coach/Parent answers and existing saved squads are not rewritten. Removing one Parent while another remains eligible preserves automation. Queued notification delivery revalidates current authority.

Existing eligible adult self-response automation is preserved through the same authoritative event-contact function. A missing Parent alone never confers adult eligibility: current verified adult account link, contact scope and eligible account rules must pass. Parent-dependent invitations without an eligible Parent are suppressed.

Simon approved durable retirement after loss of the last eligible responder (1790966163.558539, replying to 1790966116.133839), and reiterated that every feature is optional by the Team Admin (1790966181.156219). A separate retirement ledger permanently stops applying the original automatic deadline after relinking. Nondeferred source triggers capture loss within Parent/adult link, Player contact/status, membership and eligible auth-account mutation transactions, including unlink/relink between worker runs. A transaction gate serializes source writes, delivery-window capture and deadline commits; stale repeatable-read mutations must retry. These hooks make no ledger or gate writes in the default OFF state. Ordinary auth sign-in timestamp changes do not fire them.

Retirement does not rewrite explicit answers, saved squads/plans, jobs, audit effects or accepted/held delivery history, and never replays old notices. A newly created recipient invitation source, created after retirement and subsequently confirmed delivered, can open a fresh response window for the same event/occurrence. An append-only source ledger binds all confirmed recipients to their shared window. Old source identities cannot reopen or join a fresh window after resending, timestamp changes or policy changes, and only the fresh window's confirmed sources authorize its notifications and planning. The new window starts at its own first delivery; queued sends cannot enrol. Any existing explicit answer still wins. MATCH retains its per-recipient uniqueness and TRAINING retains its shared per-occurrence request. An ordinary resend to the same recipient reuses a source and stays retired; this change adds no source deletion or same-recipient renewal action. Retirement is a lifecycle safeguard for an opted-in feature, not a separately bypassable strictness option. The current Coach-rank configuration permission is retained pending clarification whether Simon's Team Admin wording requires restricting configuration to Team Admin and higher.

## Local implementation

The web Coach home links to shared team settings through a separately gated route; Coach mobile has a compact settings section. Web Coach/Parent/Adult Player and Coach/Parent mobile reads carry separate automatic provenance and correction labels. Existing invitation delivery states and explicit response records are preserved. New match selection, linked formation versions and formation publication are guarded in PostgreSQL. Existing selected squads and saved plans are not rewritten. Training read models expose planning exclusion without changing historical attendance.

One additive migration defines scoped policy RLS, optimistic revisions, idempotent save commands, disabled release control, future-only source delivery triggers, immutable enrolments, bounded candidate scanning, durable jobs/effects/outbox, authoritative context checks and minimal authorised projections. No backfill or cron is installed. The two unreleased draft stages are consolidated into one migration to meet the existing single-migration scope gate; no applied migration is changed. The endpoint process-team-coach-reminders is separately disabled and requires the existing scheduler secret when enabled.

Jobs are replanned from current canonical events and recurrence metadata. Cancelled/deleted/past/TBC events, removed memberships, revoked/cancelled request sources and excluded training occurrences fail closed. London calendar-day squad timing preserves wall time across DST. Ambiguous or nonexistent starts are skipped. A canonical training reschedule cannot rely on an obsolete request occurrence timestamp. SQL selection guards use the same current occurrence rules.

Context is checked at commit and again before delivery. Logical recipient keys survive rescheduling. Accepted or held sends cannot be reopened. Resend providers receive durable hashed idempotency keys, and inbox writes deduplicate. An interrupted or uncertain send, lost lease, or expired claim is held for reconciliation instead of blindly retried. Expo has no provider idempotency contract, so a send interrupted after provider acceptance must remain held until reconciled. Training requires at least one delivered, unrevoked, unexpired source for the enrolled request/player/scope; losing all sources suppresses planning, effects and delivery. Removing one parent's source preserves the other parent's valid shared invitation.

Each processor invocation scans at most 30 candidates, processes at most 30 due jobs and attempts at most 30 pending notifications. The scan cursor advances one candidate at a time. A separate durable cursor rotates planning, jobs and delivery so each stage starts first once per three invocations, including after interruption. Future jobs do not occupy the due-job batch. The 18-second soft budget stops starting additional stages/items. If its first-priority job/outbox list succeeds after that budget, exactly one item can still start when at least five seconds remain before the 25-second request deadline. No item starts with less reserve. The deadline includes authenticated setup/imports and cancels database HTTP calls, SDK retry/backoff waits, Resend and Expo requests. It uses a conservative bound below Netlify's documented 30-second scheduled and 60-second synchronous limits; the actual deployed site timeout still requires a non-sending release check. No native scheduler is installed.

The five-second reserve is an admission bound, not a claim that an item always finishes in five seconds. Supported slow-list progress requires the priority list plus setup/rotation to complete within 20 seconds, followed by the item completing before the 25-second deadline. Later items additionally require remaining soft budget. Longer lists safely defer, and aborted discovery can require cursor wrap before a source is revisited. Cancellation of a write or provider send cannot prove server-side nonacceptance: CAS/idempotent ledgers and claimed-send leases remain authoritative, and expired/uncertain claims are held for reconciliation. Monitor interrupted/failed invocations, list/commit/provider latency, candidate/job/outbox age and held claims; repeated deadline exhaustion requires an operational latency/backlog remedy before activation. No progress bound is asserted during sustained outages or excessive latency.

For a stable population and fast successful operations, 900 candidates are visited within 30 scan invocations plus a wrap/reset invocation. With slow operations, completed scans can fall below 30 per invocation; planning receives first priority every third invocation, so a stable N-source population can require up to 3N plus a reset invocation when only one candidate completes in its priority slot. Queued jobs and delivery receive the same rotating first priority. These bounds assume finite successful operations, a stable population and ongoing invocations; outages, ongoing arrivals and delivery backlogs require measured lag monitoring. No polling interval or delivery SLA is selected by this draft.
